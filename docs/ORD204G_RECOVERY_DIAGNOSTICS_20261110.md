**Confirmado.** La tarea Windows emitió el evento 129, registro 2082 y PID 15672. La salida observada fue 2. El segundo lanzador no dejó el JSONL ordinario y el ledger conservó un solo claim. El primer ejecutor había guardado plan 1 y checkpoint 2. Después de la interrupción, el lease expiró naturalmente y el token obsoleto fue rechazado. La misión anterior terminó cancelada. Véase [PR #219 y su evidencia](https://github.com/Victoriosas/autopilot/pull/219).

**Descartado para ese intento.** El lease activo no explica la ausencia de un segundo claim: la lectura previa mostró el lease expirado. La CLI y PostgreSQL solo se invocan después de abrir y sincronizar el registro ordinario. La evidencia disponible sitúa el fallo antes de ese punto. La comprobación posterior no encontró desalineación persistente de SHA ni del hash de configuración.

**No demostrado.** El código 2 agrupaba errores de manifiesto, rutas, binarios, configuración, Git, historial, consulta y correlación del evento 129, y apertura de auditoría. El evento del PID 15672 fue legible posteriormente. Su disponibilidad y unicidad durante el preflight original siguen indeterminadas. También siguen indeterminadas una carrera de publicación del evento, una lectura transitoria fallida y un error de permisos o archivos. No se cambian la espera, la ventana de consulta ni la política de coincidencia única sobre la base de esas hipótesis.

## Instrumentación y regresiones

- El argumento fijo de la tarea, `--diagnostics`, elige un directorio local preparado con ACL privada para la identidad del lanzador. La ruta es independiente del manifiesto. Cada invocación crea un archivo exclusivo `<uuid>.preflight.jsonl` con escrituras sincronizadas para inicio, rechazo y cierre. La invocación comparte UUID y PID con el registro ordinario.
- Los diagnósticos contienen solo UTC, UUID, PID, etapa, código estable y salida. PowerShell distingue historial desactivado, error de consulta o lectura, coincidencia ausente y coincidencia ambigua. La salida del lanzador sigue siendo 2 para estos rechazos. Si falla la apertura o el primer registro, se rechaza el lanzamiento. Si falla una escritura posterior, se emite un aviso saneado sin cambiar el resultado del ejecutor. Un fallo anterior al arranque de JavaScript o un cierre forzado puede dejar el diagnóstico ausente o incompleto.
- Las regresiones ejercitan rechazos del CLI, concurrencia de invocaciones, ausencia de volcados de entradas, manifiestos y configuración alterados, y el contrato de PowerShell para evento único, ausente o ambiguo. El scheduler y el ledger mantienen sus controles de concurrencia y fencing.
- La identidad fija preparada es `synthetic-native-ord204g-recovery-20261110`, con objetivo y recursos sintéticos existentes. El manifiesto rechaza el ID cancelado. El preparador exige SHA limpio y límites absolutos explícitos, genera una definición deshabilitada y la valida con el parser de Windows sin registrarla. El controlador del laboratorio usa un límite absoluto de cierre con margen para detener el servidor.

## Ventana y comprobación pendiente

La ventana del 10/11/2026 tenía primer disparo a las 19:37:43, fin de disparos a las 19:57:43 y cierre máximo a las 20:05:43 (Uruguay). Al comprobar el host a las 19:43, el primer disparo ya había pasado y la reparación estaba sin validar. La ejecución operativa requiere otra ventana absoluta y el SHA de esta propuesta aprobado. El historial de Windows se observó habilitado. La evidencia del cierre previo registra que la elevación de restauración fue cancelada por el usuario o el sistema.

Para preparar la próxima ventana, proporcionar `ApprovedSha`, `OutputDirectory`, `StartAt` y `EndAt` a [Prepare-NativeDemo.ps1](../tools/native-host/Prepare-NativeDemo.ps1). Usar una carpeta nueva y los horarios aprobados. Indicar `PsqlPath` si PostgreSQL no figura en PATH. `StartAt` es el primer disparo, no la apertura administrativa de la ventana. Comprobar que la definición sigue deshabilitada y que el puerto dedicado está libre. La admisión debe usar el nuevo `mission-request.json` y el perfil de propietario del laboratorio. Pasar la carpeta de propuesta y el cierre absoluto al controlador dedicado. Para la aceptación, conservar ambos eventos 129, ambos claims, expiración natural, rechazo del token anterior, reconciliación sin duplicación, avance del checkpoint, estado terminal y limpieza. Cualquier nuevo rechazo debe correlacionarse con el UUID y el PID antes de cambiar el control que lo produjo.

La reversión consiste en cerrar la PR o revertir su commit antes de una aprobación operativa. Si existiera una tarea de prueba en una ventana aprobada, deshabilitarla y retirarla, detener la instancia dedicada y conservar evidencia y estado terminal. La integración depende de la base de PR #213. El trabajo de disponibilidad F1 se sigue en PR #218 sobre #217.
